# Product photo upload and merchandise activation — prepared, not deployed

Client staff enter and manage the catalog through Owner admin. No developer catalog collection/import is required. This change addresses the photo/activation blocker only. Production checkout, every payment method, operational recovery, both checkout/recovery build flags and noindex are unchanged. Production anonymous signup remains disabled; its actual anonymous Auth verification remains pending. Earlier disposable anonymous checkout evidence is separate from the pending media acceptance below.

## Failure and local fix

The image picker was deliberately hard-disabled after the 15,425,791-byte pinned WASM deployment failed (oversized server bundle and Docker deployment timeouts; `.tmp/validator-deployment-support.md`). Separately, migration 007 permanently required new drafts to be samples, while checkout rejects samples. Uploading a photo could not resolve that activation dead end.

The same ImageMagick 0.0.45 decoder, independent byte decoding, dimensions, MIME/header checks, metadata stripping and responsive WebP generation remain. A prepared 424,810-byte JavaScript bundle loads the exact pinned decoder from a new **private** bucket. Its compressed object is 5,428,719 bytes; decompression is bounded to exactly 15,425,791 bytes, SHA-256 checked, and WASM validated before initialization. Missing/corrupt assets fail closed. The preparation uses native ESM package exports; an initial CommonJS helper bundling failure was caught by the actual-bundle test and corrected. No hosted success is inferred from the smaller artifact. [Supabase bundle guidance](https://supabase.com/kb/troubleshooting/edge-function-bundle-size-issues).

Owner UI requires both `BATOOL_PRODUCT_MEDIA_RELEASE=true` at build time and an authenticated `GET validate-product-image` response with the current `batool-product-image-v2` readiness contract. The endpoint verifies Auth and the live Owner mapping, initializes the pinned decoder, and checks the new Owner-only database readiness RPC. Missing deployment/schema/configuration leaves selection/upload/approval disabled. Alt-only edits on existing validated images remain supported.

New migration **`20261102001400_product_media_activation.sql`** is necessary. Applied migrations 001–013 are untouched. It creates the private decoder bucket/policy and a private current merchandise-approval witness, adds revision-checked Owner approval, and replaces only the catalog guard and checkout snapshot definition. The snapshot's existing OID, service-only grants, prices, shipping, lock order and retry handling are retained; its original source fingerprint must match before replacement. No existing products, receipts, stock, orders, policy terms or readiness/payment flags are updated or automatically approved.

Approval locks the live Owner mapping, product, then ordered variants; it requires saved fields, known nonnegative S/M/L/XL stock (zero is valid), this product's trusted receipt, alt text and all three validated objects. A browser cannot forge the private witness or clear sample status directly. Approval does not activate the product or enable ordering. New drafts require approval before activation. Changing the main photo makes a product inactive/sample atomically, requiring new approval; alt-only edits retain approval. Conflicts/lost responses require reload/review, not a blind write with a new revision. Existing identities, slugs, illustrative fallback disclosures and immutable prior image objects remain retained. Checkout now independently requires the private approval, trusted photo and known stock, so UI/build flags cannot make samples or image-less/unknown-stock merchandise orderable.
