# BATOOL architecture and next steps

## Phase 1: component foundation

- Real Next.js App Router with strict TypeScript, not a client-side rewrite inside one giant component.
- Layout, product pages, help pages and editorial sections use Server Components. The current static export renders them at build time.
- Catalog edit filters, search, sorting, size controls and cart interactions use Client Components. Edit selection uses `useSearchParams` inside a Suspense boundary; native history updates preserve local search/sort state and synchronize Back/Forward navigation. Only the cart trigger and open drawer subscribe to cart state; the page and catalog do not.
- An external browser store uses `useSyncExternalStore` with stable snapshots and an empty server snapshot. It restores local storage after subscription, validates data, migrates old `qty` records, and responds to changes in another tab. The first storage write failure switches the store to an in-memory-only bag for the rest of the page session. Actions, storage events and resubscriptions then never restore persisted data or retry writes, so stale storage cannot overwrite unsaved changes. Unsaved changes cannot survive a full page reload. When writes work, restoration and cross-tab synchronization remain enabled. The React hooks use the same cart-model store factory exercised by the Node regression tests.
- Product cards receive stable product references and use `memo`, so search and sorting do not rerender unchanged cards. Size selection lives in the purchase control. Cards use a scoped 3:4 image frame and per-product card focal positions. Their Quick Add dialogs keep selection/open state local, call the existing cart action and never subscribe to the cart; stitched options require explicit selection. Existing native dialog behavior handles Escape, focus containment and restoration. Genuine alternate product images are not available, so no simulated secondary views are shown. The cart drawer is dynamically imported when opened.
- Node regression tests cover totals, independent sizes, quantity limits, bad stored data, migration, query composition, immutable sorting, and production store persistence, storage failures, subscriptions and cross-tab updates.
- The lazy-loaded bag drawer has scoped empty, populated and demo-checkout presentations. Its compact header remains outside a single scrolling content area; subtotal/checkout are omitted when empty. Item totals reuse the pure cart subtotal function, and keys include size. Quantity/removal announcements follow committed store snapshots; removal focus targets the next surviving line, previous line or empty collection CTA. Native dialogs retain modal focus behavior and immediate dismissal, with shared reference-counted background scroll locking that restores prior inline styles and scroll position on cleanup. Node tests cover focus-target selection with the production store and scroll-lock restoration; actual browser focus/scroll behavior still requires browser verification.
- Product details remain Server Components with a single optimized portrait with disclosed sample-image reuse where applicable, clearly labeled concept copy and native information disclosures. Only purchase selection, feedback and bag opening use client state. Product pages and Quick Add share the cart-independent purchase policy in `catalog/model/purchase.ts`; the Quick Add exports remain compatible. Every stitched piece starts without a selected size and requires an explicit choice. The purchase control calls the existing cart action without subscribing to cart state, and opens the existing dynamically loaded drawer. Short viewports and expanded disclosures use normal document flow; product sticky positioning is limited to desktop viewports at least 1000px tall with disclosures closed and accounts for the sticky navbar height.

## Rendering policy

Necessary rerenders are normal. The goal is to avoid broad subscriptions, unstable props, duplicated derived state and expensive work. Do not add `useMemo` or `useCallback` everywhere. Searching the eight sample products is trivial; pagination, server search and virtualization are deferred until catalog size and profiling justify them. React Compiler can be evaluated later with measurement; it is not needed to explain or enforce these boundaries.

Use React DevTools Profiler on a production-like build before asserting a rerender or CPU improvement. No Core Web Vitals score or zero-rerender claim has been established by this migration. React/Next.js adds framework JavaScript compared with the original plain HTML prototype; this architecture improves maintainability and prepares routing/data integration, not a guarantee of a smaller total JS payload.

## Asset policy

`next/image` supplies image dimensions, responsive source selection and lazy loading. The initial hero image has high fetch priority; product-page lead images are preloaded. A custom loader points to build-time WebP variants because static exports do not provide the default Next.js image optimization server. Source PNGs remain outside public assets. The image pipeline emits sixteen product variants and three stitched desktop campaign previews. Three hero image pairs are independently configured in `features/campaign/model/slides.ts`: Gulnaar, Meher and Noor, each with a different desktop/mobile source and identical headline copy. Autoplay advances every seven seconds; Pause/Play controls rotation, and manual navigation preserves that setting. Keyboard focus pauses rotation until explicit Play. Exact replacement filenames and compositions are listed in `src/features/campaign/README.md`.

Individual outfit panels are 384 pixels wide; generating larger product images would not recover detail. The hero uses separate portrait panels on desktop and mobile. The desktop layout places each portrait on the right with a masked blend into the plum background. The pipeline also retains optional contact-sheet overview variants. Replace sample imagery with high-resolution client photographs before launch, then expand the image pipeline and sizes. Fonts use `next/font/local` with licensed Cormorant Garamond and DM Sans WOFF2 files checked into `src/app/fonts/`. The root layout defines shared serif and sans variables: editorial headings and product names use Cormorant; navigation, body copy, prices, controls and utility headings use DM Sans. Clean builds and development rendering need no Google Fonts access. Provenance, weight choices and hashes are documented alongside the assets; SIL OFL notices are included in `public/font-licenses/` and the static export. `turbopack.root` explicitly points to the directory containing `next.config.ts`, keeping the standalone app independent of unrelated ancestor lockfiles.

## Current limits

- Static export: no runtime Server Actions, API routes, ISR, accounts, stock management or secure checkout.
- Local cart is convenience state and is never authoritative for prices or stock.
- No real orders, payment collection, fabricated delivery promises or customer contact data.
- Preview pages are marked noindex. Change metadata and canonical settings intentionally for a real launch.
- Existing global visual styles are retained to preserve the design; new reusable image styles are scoped. Further style extraction should be feature-by-feature, with visual regression checks.
- Product pages are pre-generated. Adding products requires a build until a backend rendering strategy is selected.

## Subsequent phases

1. **Visual refinement:** extract remaining feature styles into CSS Modules, refine mobile product pages, add real photos and validate keyboard and screen-reader flows.
2. **Measured performance:** record production bundle sizes, Lighthouse and field Core Web Vitals where available; profile the catalog/cart; make targeted changes against that baseline.
3. **Real commerce:** choose a commerce backend, wire the repository to verified catalog data, add server-side price/stock checks, choose payment/COD and shipping providers, handle checkout idempotency and verified payment webhooks.
4. **Launch readiness:** confirm policies and contact details, add error monitoring, transactional order flows, accessibility tests, analytics consent as applicable, and end-to-end tests against a sandbox checkout.

Do not add backend services or providers until the client's real operational requirements are known.

## Verification in this environment

The production export was checked in the browser for product navigation, size selection, persisted bag migration, quantity totals, demo checkout and catalog search. The managed Next development preview rendered HTML but did not respond to interactions; the same production export did respond correctly. Development-server behavior should be verified locally in VS Code. No mobile-device performance audit or React Profiler benchmark has been claimed.

## Stitched-only frontend scope

The catalog contains only stitched 3-piece ready-to-wear in S, M, L and XL, with eight illustrative products: Gulnaar, Meher, Saba, Noor, Mira, Amanah, Layal and Zeenat. Product `category` stays Stitched; `subcategory` assigns Daily Pret, Festive Edit or Luxury Formals. A shared list adds All 3-Piece for header/footer navigation and catalog filter controls. Collection links use the category query plus `#collection`; unknown query values fall back to All 3-Piece. Search includes subcategory names and RTW badges, and composes with filters and immutable price sorting. Card badges use the product's tag, while noninteractive size pills render its actual size options. Every product has a distinct imageSlug and decodable 192px/384px WebP assets, shared by cards, product pages and the demo bag. Mira reuses Meher's full portrait with a distinct editorial card zoom, placed in the second featured row. Zeenat is a festive concept using the disclosed Gulnaar portrait with a subtle zoom. Amanah and Layal repurpose the restored generated styling images as stitched velvet and silk formal concepts. Every product description specifies Stitched Shirt, Trouser & Dupatta. The brand narrative is followed by three fit and tailoring highlights, including interior seam allowance, 48-hour dispatch and 7-day size exchange. The source contact sheet and public images contain only retained stitched products. Provenance is recorded in `assets/source/README.md`; optimization is reproducible offline. Existing IDs remain 0, 2, 3 and 7; stitched Noor uses ID 8, with new formal/festive SKUs 9, 10 and 11, so cart validation discards unavailable items without assigning their IDs to other products. Tests cover this migration, subcategory destinations and filtering, badges, image decoding, consistent portrait proportions and disclosed image reuse. No API, account service, payment integration or order submission has been added.
