## Behavior and boundaries

Owner can create a named, described, priced **inactive stitched 3-piece draft**, with exactly S/M/L/XL variants. Unknown stock is SQL NULL; zero and positive integer stock stay distinct. A new draft has **no image or borrowed local photograph**. Collection, card label and the existing card accent color can be completed later; the accent is presentation metadata, not a color variant. Drafts remain concept/demo content with a fixed brand-confirmation disclosure.

IDs come from a private integer sequence initialized under a database table lock above existing IDs, with minimum 12. IDs 9/10 are permanently rejected by a table constraint. The server generates a bounded lowercase ASCII slug with its allocated ID suffix, retrying unique-slug conflicts; non-ASCII-only names use `product-ID`. Renames never change slugs. Identity, local-image identity, demo flag and concept disclosure are immutable.

Creation is one Owner-authorized transaction: product, four variants and an Owner-scoped UUID request record. Concurrent retries with the **same key and normalized payload** serialize on a transaction advisory lock and return the same product. Reusing a key with changed values is rejected. Different keys are separate intentional creations, not content deduplication. A failed transaction leaves no product/variant/request record; sequence gaps are normal. Requests reference the originating Auth identity and are retained; deleting that identity requires a separately reviewed retention workflow.

The form retains an unresolved request in memory and locks its inputs. **Retry draft creation** resends the same key/payload, including after an invalid success response. Access clearing/tab reload loses this in-memory attempt; review existing drafts before starting a new request after an interruption. There is no automatic retry with a new key and no persistent product-data cache.

Saves remain revision checked and atomic. Owner can archive/unarchive; archive requires inactive status and retains the product, variants and images. Unarchiving does not automatically activate. Hard product deletion/truncation and variant identity changes are blocked. Partner/unassigned/anonymous users cannot create or save. Browser roles have no direct writes or sequence/request-table access. Definer RPCs have an empty search path and lock the live Owner mapping before validation/writes.

Activation requires valid product copy/PKR price, collection, card label/accent, all four active size variants, unarchived status and a product-specific image. New products require a trusted receipt, matching dimensions, alt text and all responsive Storage objects. The six original products retain only their own existing local-image fallback identities and disclosures. No image receipt can be forged by a browser, and another product's receipt is rejected.

**Upload and activation blocker:** hosted trusted validation remains blocked/unverified. File selection/upload controls are disabled with an explanation. New drafts without a trusted image remain inactive. Existing immutable images and alt-only editing are retained. SQL/JS image-path validators now accept existing IDs or allocated IDs ≥12, while keeping UUID/product binding, reserved-ID rejection, receipt authorization, byte decoding, MIME/size checks and Storage immutability. No validator deployment was retried or bypassed; the shared validator source would require separate future deployment/acceptance before uploads can be enabled.

**Saving never publishes.** Anonymous catalog policies exclude inactive products and their variants; the build reads active products only. New public routes need a successful rebuild and deployment after activation. Archiving cannot remove data from an older deployed static export. Checkout, notifications, commissions and size/color-variant models are unchanged.
