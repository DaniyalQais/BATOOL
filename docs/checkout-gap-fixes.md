## Actual failure cases and fixes

**Non-checkout order references.** 012's verifier checked only `public.orders` existence. A complete order created under the earlier foundation schema can lack a checkout quote/context, so its case could become verified/committed even though the support-result builder could not construct a checkout receipt. That was a functional dead end, not authorization to repeat stock deductions or create a replacement.

New forward **`20261102001300_checkout_recovery_order_validation.sql`** adds a private predicate requiring a matching order, consumed checkout quote, checkout details and retry identity in the same scope. Public verification remains live-Owner-only and retains original attestation/evidence/revision checks. An unsupported reference is audited/escalated instead of accepted. The resolution wrapper also catches cases verified or labelled committed by 012 before the fix: with current Owner/session, policy, revision and expiry checks, it escalates only the support case. It never modifies the existing order/stock or creates a replacement. Valid checkout order recovery continues through the exact preserved 012 implementation. Private legacy helpers and predicate are not callable by application roles.

013 changes function definitions/ACLs only; installation rewrites no existing row or readiness flag. It was applied once only to disposable **`jcbxxgjrnkhgcspbscgb`**. It is **pending manual BATOOL review/application**. SHA256: `3f1fa81903caec6c5204de794032de08381c414b0bfb554c3ecced41b96aa1dc`. Prepared [preflight](../supabase/tests/recovery_order_validation_preflight.sql) / [postflight](../supabase/tests/recovery_order_validation_postflight.sql) are combined read-only queries: preflight rows 01–03 PASS and row 04 saved counts; postflight rows 01–03 PASS and row 04 identical counts. A later manual sequence must review results before one application; no remote production migration was applied here.

**Availability/admission identity.** Previously `availability` returned before `checkout_admit`, permitting repeated calls without the application limiter. Other actions derived their bucket from the first `x-forwarded-for` value without a verified gateway trust contract; an accepted spoof could choose fresh per-address buckets (the global ceiling still existed).

The handler now admits availability before readiness is read or returned, including while intake is off. Limiter denial returns sanitized 429; transport/malformed limiter failure closes with 503. No raw readiness/private settings are exposed. Address headers are completely ignored: two fixed server-selected HMAC cohorts, `availability` and `checkout`, use the existing 30/minute bucket and 120/minute global limits. That is 30/minute **across shoppers per cohort**, not per customer. No request field/header chooses another identity; no address is stored/logged. Origin/body/scope/Owner authorization, database readiness, escrow-before-create and independent commit/recovery checks are unchanged. High load can rate-limit recovery; capacity approval remains a launch decision rather than an invented throughput guarantee.

The user confirmed production origin **`https://batool-lake.vercel.app` only**, excluding chatgpt.site and unconfirmed custom domains. Layout metadata and home/product/help canonical links now align locally. Noindex remains unchanged. Static export and existing hosting are preserved; changing metadata did not authorize publication.
