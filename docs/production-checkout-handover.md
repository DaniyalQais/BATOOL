## Operational recovery procedure — prepared, not implemented or rehearsed

The current guest token permits normal actions for seven days from issuance; `recover` and `resolve` accept a correctly signed token for an additional 23 days after its embedded expiry (normally 30 days from issuance). This is token-relative, not an order-age guarantee. New intake can be off while recovery remains available. The handler has a single signing secret and no authenticated operator recovery/reissuance endpoint. Expired or missing tokens cannot be bypassed by the existing public flow.

1. **Contain uncertainty.** Preserve the cart and saved intent. Ask the customer to keep the same tab and use **Check saved order** / **Resolve saved checkout** when the capability is still accepted. Do not clear storage, issue a fresh key, re-add stock or suggest a second order because a response was lost. Tell the customer the order outcome is unconfirmed until reconciliation completes.
2. **Open a private case.** Use an Owner-approved private support route and independent requester-verification procedure. Record case ID, authorized operator, time, minimal evidence category, related order reference and decision in access-controlled audit storage. The identity-verification rules and audit tool still require implementation/approval; an order reference alone is not proof of identity. Do not ask for browser capability/retry keys, Auth passwords/tokens, PINs, OTPs or wallet logins in messages. Never log request headers, complete customer records or bearer secrets.
3. **Look for an existing committed order.** An authorized Owner retrieves saved orders using existing protected Orders/detail/context readers and minimal private details for verified reconciliation. Preserve ambiguous matches for investigation. If committed, return its existing reference/status through the verified support route. Do not create a replacement purchase, change monetary snapshots, cancel/refund, repeat stock deduction or mark a wallet paid to repair a lost confirmation. This step can recover status even when retry credentials are gone, provided the requester/order can independently be established.
4. **Resolve only a provable original identity.** An authenticated, narrowly authorized backend recovery tool is still required when the public capability is unusable. It must establish the original scope/key/quote through protected evidence; never accept a customer-supplied scope UUID as authorization. Original retry keys are stored as hashes and cannot be reconstructed from those hashes. Securely held original intent evidence may permit resolution; an order lookup or isolated missing-row response does not prove an uncommitted attempt is safe to replace.
5. **Serialize before replacement.** The future tool must call existing `checkout_resolve` with that exact scope/key/quote. It shares the creator's scope/key advisory lock and locks the quote, so concurrent creation completes or blocks before retirement. It returns an existing committed receipt or durably records retirement and invalidates only the uncommitted quote. Re-read via `checkout_resolution` in a separate committed request; match status, quote, resolution ID and replacement key as the existing Edge handler does. Timeouts/errors leave the case unresolved: repeat the same identity, never generate another. A committed or consumed quote must not be invalidated.
6. **Reuse the pinned replacement.** Only confirmed retirement permits the same scope's recorded resolution and server-assigned replacement key. Issue any recovery capability only through the authenticated audited backend, following the approved identity policy. `checkout_replacement_quote` pins one quote to that resolution/key; retry lost responses using it. Show fresh prices/shipping/policy and collect delivery details again. If the successor also expires, resolve that successor's own exact identity rather than bypassing the pinned mapping. The customer sees success and cart consumption only after independent committed-receipt confirmation. Never put credentials in URLs or ordinary support messages.
7. **Escalate unavailable evidence.** If the original identity cannot be established, or matches conflict, keep automated replacement blocked and escalate for manual reconciliation. Do not interpret a momentary absence as proof no order can commit. Outside the capability window, missing credentials, or signing-secret loss require the authenticated process above; there is currently no implemented general automatic recovery route. Document unresolved cases and do not promise a recovery time that has not been approved.
8. **Protect signing keys and mappings.** Store the production signing secret durably in restricted backend secret storage with an approved recovery/backup policy. Do not rotate/delete it casually: the current verifier accepts only one key, so replacing it strands previously signed capabilities even inside their recovery window. A versioned multi-key verification/retention design and audited reissuance path are required before claiming seamless rotation. Preserve quotes, retry identities and retirement/successor mappings needed for recovery; do not prune consumed quotes as unused expired quotes. Never disable triggers or remove committed orders to clean up a case.
9. **Rehearse only the missing operational flow in disposable hosting.** Once the operator tool and policy exist, verify requester mismatch/denial, absent original identity, expired capabilities, signing-key recovery/rotation, operator revocation, audit redaction and lost operator responses. Confirm the original committed order/stock stay unchanged and replacements require durable retirement. These are pending new operational checks; do not rerun completed guest acceptance or use BATOOL fixtures.
