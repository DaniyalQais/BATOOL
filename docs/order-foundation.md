## Tables and read access

| Table | Stored data | Owner | Partner | Unassigned/anonymous |
| --- | --- | --- | --- | --- |
| `public.orders` | UUID, creation/update dates, PKR monetary amounts, fulfillment/payment status and status revision | Read | Read; reporting surface | No rows for unassigned; anon has no SELECT grant |
| `public.order_items` | Product/variant reference and immutable order-time name, selected size, unit price, quantity, generated line total | Read | No rows | No rows; anon has no SELECT grant |
| `public.order_customer_details` | Recipient, phone, optional email, structured delivery address | Read | No rows | No rows; anon has no SELECT grant |
| `public.order_status_history` | Old/new status, revision, date, JWT actor UUID and database/session roles | Read | No rows | No rows; anon has no SELECT grant |
| `public.order_creation_keys` | Opaque retry scope, key hash, canonical request digest and linked order | No grant | No grant | No grant |

`orders` is a physical table containing **only report-safe data**, rather than a definer view over customer records. No customer ID, email, phone, address, product/item detail, actor, payment reference, note or retry digest belongs there. Future reports must aggregate this surface without joining private data into a Partner-accessible object. Bigint money is integer PKR paisa; 100 paisa = PKR 1. Future JavaScript code must preserve bigint values as exact strings/BigInt, not round them through Number. No commission fields, rates, settlement tables or calculations exist.

All five tables enable RLS. An `authenticated` table SELECT grant does not grant every signed-in person rows: policies require a non-null `auth.uid()`, a non-anonymous session, and that same user's live `dashboard_roles` mapping. Only `orders` accepts `owner` or `partner`; private operational tables require `owner`. Unassigned users, spoofed user metadata and anonymous Auth sessions are excluded. Role removal/demotion changes subsequent reads. The existing self-only role policy supplies the role mapping; no new role-assignment capability is added.

Direct Data API queries and relational joins must pass both PostgreSQL grants and RLS. Partner joins to private tables return no private rows, including embedded relationships; an inner join may consequently suppress the report row, which is not authorization failure. No materialized report, definer view, public read RPC or Realtime publication is added. GraphQL/introspection may reveal schema metadata; it is not customer-row access. Infrastructure administrators remain trusted and can override permissions; an application Owner is not a database administrator.

This follows Supabase's separation between [table privileges and RLS](https://supabase.com/docs/guides/api/securing-your-api) and its guidance to use the [verified user ID and protected role data](https://supabase.com/docs/guides/database/postgres/row-level-security), rather than editable user metadata. Secret/service-role credentials bypass RLS but still require table grants; migration 006 revokes those grants on its new tables too. No browser should ever receive administrative credentials.

## Snapshot and transaction invariants

- The catalog variant composite FK guarantees a retained product/size reference. The historical name, selected size, price and quantity live on each order item; a later catalog rename, price change or deactivation cannot rewrite them. Item UPDATE/DELETE/TRUNCATE are blocked by triggers. Product/variant deletion is restricted by the historical reference.
- Quantities are positive integers; sizes are S/M/L/XL; prices and fees are nonnegative bigint minor units. Generated `line_total_minor` uses integer multiplication; overflow rejects the write. `total_minor = subtotal_minor + shipping_minor + tax_minor - discount_minor`, with discount no larger than subtotal. Arithmetic comparison uses numeric to avoid overflow while checking totals. Fee/tax/discount/currency amounts are explicit inputs for a future trusted writer, with no invented free shipping or tax defaults.
- Deferred constraint triggers require at least one item, matching summed item subtotal, exactly one private-details row and exactly one linked retry record at the end of a transaction. Foreign/unique keys enforce the one-to-one relationships; private details cannot be moved to another order. An incomplete or mismatched order cannot commit; flushing with `SET CONSTRAINTS ALL IMMEDIATE` makes a test inspect this before rollback.
- Order identity, creation timestamp, currency and all monetary snapshots cannot be updated. Deletion/truncation is blocked. Corrections, line additions, cancellation stock returns, refunds and data retention need separately approved workflows; do not disable triggers for ordinary operations. In this phase all writes require trusted SQL administration, exclusively for isolated fixtures—not real order intake. An administrator can still add rows within the invariants; immutability here prevents rewriting saved snapshots, not malicious DBA action.
- Retry records are immutable, unique on `(scope_id, key_hash)` and on `order_id`. Raw tokens, request bodies and customer contact data are not stored in this table. Digest format/uniqueness does not itself implement retry handling; no endpoint exists yet.

## Status model and audit

These are conservative database transitions prepared for review before checkout. They do not select a payment method, courier, SLA or shipping promise.

| Domain | From | Permitted next states |
| --- | --- | --- |
| Fulfillment | `pending` | `confirmed`, `cancelled` |
| Fulfillment | `confirmed` | `packing`, `cancelled` |
| Fulfillment | `packing` | `shipped`, `cancelled` |
| Fulfillment | `shipped` | `delivered` |
| Fulfillment | `delivered`, `cancelled` | Terminal |
| Payment | `unpaid` | `paid`, `failed` |
| Payment | `failed` | `unpaid`, `paid` |
| Payment | `paid` | `refunded` |
| Payment | `refunded` | Terminal |

Orders begin `pending` / `unpaid`, revision 1. Initial creation emits two history events. Each accepted UPDATE must change at least one status, validate each changed domain and advance the server-managed revision once. Changing both domains emits two events sharing that revision. Timestamps are database assigned. Fulfillment does not silently mark payment paid; cancellation does not automatically refund or restock. Paid cancelled orders are possible until an explicit refund is recorded. Shipping does not imply payment, and payment does not imply delivery. Returns, failed delivery, partial payment/refund and reopening terminal orders are intentionally unsupported pending business decisions.

Only the `orders` trigger inserts history. Direct history INSERT, UPDATE, DELETE and TRUNCATE are rejected; browser privileges do not allow any of them. Actors derive from `auth.uid()`, `current_user` and `session_user`, never submitted actor fields. There is no Auth FK that could erase/change audit identity when an account is deleted. DB-only actions have NULL JWT actor and retain database/session roles. Shared `postgres` identifies an execution role, not the human Dashboard operator: use infrastructure audit logs for that attribution. A future narrow authenticated Owner command must verify/lock the live mapping before writing, preserve the verified JWT actor, compare an expected revision and authorize the particular transition. Payment changes must come from verified payment evidence or a separately approved audited administrative workflow, never a browser's `paid=true` assertion. No such command is exposed now.

## Future atomic order creation design (not implemented)

One trusted backend must perform the following inside a single database transaction. Client-side checkout totals, stock displays, payment labels and `BT-TEST-*` references are never evidence of a real order. An Edge HTTP handler alone making several independent Data API calls is **not** atomic; it must invoke a separately reviewed private transactional database operation.

1. Approve authentication/guest checkout and abuse controls first. Accept only product IDs, permitted sizes, bounded positive integer quantities, validated delivery inputs and a random retry key. Reject/ignore submitted unit prices, subtotal, shipping/tax/discount values, currency overrides, stock claims, payment status and actors. Never log raw delivery payloads or tokens.
2. Establish a server-controlled opaque `scope_id` bound to the verified caller/guest session. Canonicalize the intended request and calculate a server-side digest (prefer a keyed digest if customer data participates); the same key with a different request must conflict. Do not derive a public scope from a phone/email or accept an arbitrary browser scope. Scope issuance, expiry and digest-secret rotation are unresolved decisions.
3. Acquire a transaction-scoped advisory lock for the scope/key pair before inventory locks; digest collisions can serialize unrelated requests but must not grant access. Read an existing `order_creation_keys` record under that scope and return the saved report-safe order response only if its request digest matches. Handle a lost response after commit this way. Do this replay check **before** rechecking prices/availability that might have changed since the original order. Keep the unique key as a final race fence; a losing insert rolls back its entire attempted order and stock decrement.
4. Lock products in ascending product ID, then variants in deterministic product ID/size order, consistent with the existing product editor's parent-before-variant locking. Re-read active product and active allowed variant under those locks. Reject unavailable, reserved/retired IDs and invalid sizes. Require PKR. Reject `is_demo = true` for real ordering unless merchandise is explicitly approved via a reviewed process; all six present products are demo content. Aggregate/reject duplicate cart lines consistently. Never trust a build snapshot.
5. Require confirmed non-null stock. `NULL` means unknown and must reject real ordering; backorders require a separately approved policy. Confirm each locked variant has enough stock, then decrement with an additional `stock_quantity >= requested` condition and verify affected rows. Use checked integer quantities and amounts. Any conflict, failure or integer overflow rolls back everything. Do not introduce reservations or promise restocking behavior without approving their lifecycle.
6. Calculate unit prices from locked catalog rows. Calculate shipping, tax and discounts using approved server-side rules/quote validation; none exist yet. Derive item totals and all order totals in exact minor units. Persist the complete order, snapshots, private data and retry record together, initially `pending`/`unpaid`. Triggers generate the initial audit events. The existing variant revision triggers will also advance catalog edit revisions, protecting concurrent Owner edits.
7. Commit once; return a minimal response authorized for the retry scope, not customer details or privileged data. Retry whole transactions only on explicitly handled deadlock/serialization errors with the same key, never repeat independent stock decrements. Verify races with multiple real DB connections: last-unit contention, duplicate simultaneous retries, different payload/same key, changed catalog, failed writes and lost responses. No concurrency/overselling protection is claimed from this prepared schema alone.

No callable public creation endpoint, service-role table grants, stock mutation function, public status RPC or checkout action is introduced here. A future implementation must establish a dedicated least-privileged write boundary and tests before enabling intake. PostgreSQL functions normally receive broad default execution privileges; future functions must use explicit revokes and schema boundaries as described in [Supabase function security](https://supabase.com/docs/guides/database/functions).

## Read-only Orders dashboard

The client-rendered Orders section at `/admin/` uses the existing `adminClient()` and the signed-in user's bearer session. No orders or customer data are fetched at build time or placed in the static HTML. The section mounts only for verified dashboard access, unmounts during access rechecks/sign-out/errors and resets on account/role changes. Order data stays in component memory, without local-storage persistence or a shared data cache. Existing Owner product editing remains available below it.

`src/features/orders/model/order-reader.ts` rechecks verified identity and the live `dashboard_roles` mapping before and after a read, discarding responses if the role or subject changed. These are defense-in-depth query-selection checks; database grants and RLS remain the actual authorization boundary. There is no role parameter, administrative key or elevated client sent to the database to bypass those rules.

- Both roles read an explicit projection from `orders`, with no wildcard or embedded relationships. Partner never initiates customer, item, history or retry-key requests, and has no private-details control. The mapped report also drops unexpected fields rather than spreading raw API objects.
- Owner opens details on demand. A fresh Owner check precedes the scoped reads from `orders`, `order_customer_details`, `order_items` and `order_status_history`. There are no retry-key queries. Missing private data or a failed subrequest does not become a successful partial detail screen.
- Order lists use payment and fulfillment filters, stable `created_at DESC, id DESC` ordering, and 20 rows plus one lookahead. Items and history have independent pagination so API row caps cannot silently hide later pages. History sorts by numeric database revision descending, then status kind. Pagination is an offset-based view of current data, not a transactional reporting snapshot; refresh may move newly created orders between pages. See [Supabase range semantics](https://supabase.com/docs/reference/javascript/using-modifiers-range).
- Bigint monetary values and revisions are selected with `::text`; paisa formatting uses BigInt, without floating-point conversion. The mapper rejects numeric/rounded money responses. See [PostgREST column casting](https://docs.postgrest.org/en/stable/references/api/tables_views.html#casting-columns). Dates are shown in Pakistan time. Historical product names/prices/quantities come from saved items, not the current catalog.
- Loading, access denial, request/data errors and successful empty results are separate states. Errors never turn into zero-sales metrics or fake orders; no aggregate sales metrics are shown. Refresh/filter/page changes close details and discard obsolete responses. Empty copy states that no rows are available to the account; an empty RLS response alone does not prove that the physical database has no orders.

No order creation, status writes, exports, notifications, commission features or checkout changes were added. Static export and hosting configuration are preserved. Migration 006 and the blocked image function were not changed or deployed; Docker downloads were not retried for this dashboard task.
