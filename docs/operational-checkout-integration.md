## New migration 012 and permissions

012 adds four RLS-enabled private tables: recovery controls (disabled, no policy reference), original intent credential escrow, recovery cases and append-only audit. No application role, including Owner or service role, has direct table access. Escrow stores the exact original scope/key/quote before the backend calls creation. It contains a sensitive raw retry key; restrict administrator/backups access and approve retention. It is never returned to Owner, public clients or logs. No existing intent is guessed or backfilled. An old committed order can be recovered by its saved order reference; an old uncommitted attempt without a provable mapping cannot be replaced through this workflow.

New service-only RPCs: `checkout_availability`, `checkout_register_intent`, `checkout_support_open`, `checkout_support_result`. New authenticated RPCs: `owner_recovery_case`, `owner_verify_recovery`, `owner_resolve_recovery`. The latter three require a nonanonymous Auth-issued JWT, current Owner mapping and matching unexpired live `auth.sessions` row on every call. Partner, unassigned, anonymous and service credentials cannot act as an operator. Retained JWTs after actual logout are denied by these new RPCs; this does not change the logout behavior of older report/settings policies.

Verification and resolution use revision checks; resolution retries use the same case and return its durable result. Owner resolution reuses 010's original advisory/quote locking and cannot authorize replacement until a committed retirement exists. Multiple cases for one original identity must follow that identity's existing retirement/replacement chain; a new case is never a new purchase. No recovery path inserts an order, deducts stock, changes a saved order or marks a payment paid. Audit events preserve actor/session, policy/evidence references, decision and time without copying customer details. Audit/escrow updates and deletes are rejected.

## Operational recovery procedure

This is a **manual independent requester-verification workflow**, enforced and audited by the backend. It does not automatically prove a customer's identity. Before activation, the Owner must approve an independent verification/support procedure and an administrator records its opaque UUID reference in recovery controls. No verification, refund, delivery or tax policy has been invented. Evidence references are opaque UUIDs referring to restricted verification records; never enter PII or credentials into those fields.

1. Preserve the bag and saved intent. If the existing capability still works, use Check saved order / Resolve saved checkout. Existing guest tokens last seven days plus 23 extra days for recover/resolve (normally 30 days from issuance), unchanged by 012. A missing-order response is never restart permission.
2. For lost credentials/expired capabilities, use the support-recovery section to open a case in the current tab. The browser creates and durably saves a random case ID and 256-bit claim proof **before** sending. A lost response retries the same pair. Only the case reference is shared via the approved private support route, together with an original checkout/order reference where available. The claim proof stays in sessionStorage, never a URL or support message; the case expires after 24 hours. Never ask for Auth tokens, retry keys, passwords, PINs, OTPs or wallet logins.
3. In the Owner dashboard, load that case by reference. Independently verify the requester under the approved procedure, reconcile the exact original purchase through protected order details or the registered checkout reference, and record the evidence-reference UUID plus explicit independent-verification attestation. A case/order reference alone is not verification. The database binds that decision to the current policy, operator, session and revision. It rejects absent attestation/evidence or stale revision. If the original identity is missing or ambiguous, choose escalation; missing registered references also escalate automatically. Replacement stays blocked.
4. Resolve the verified original attempt. For a saved committed order, recover its existing receipt. For a registered intent, the database waits on the original creator's scope/key advisory and quote locks; it returns a committed order or durably retires only an uncommitted quote. A consumed quote cannot be invalidated. Timeout/lost response: reload/retry **the same case**, never generate another purchase identity. Owner sees only case status/audit, not retry credentials.
5. The requester checks that same support case using their browser-held proof. The backend independently reads the committed case outcome twice and checks the resolution identity before returning a receipt or reissuing a scoped capability for the recorded retirement. This supports verified recovery after loss of the old signing secret without accepting an arbitrary customer scope. Only the recorded resolution and pinned replacement key/quote may be used. Review fresh trusted prices/shipping/wording and re-enter delivery details; creation is still blocked while intake/method gates are off. A committed receipt without the original local cart snapshot does not clear an unrelated bag.
6. Lost/expired support proof: open a new **verification case**, which does not close or replace the original checkout. Independent verification is required again; exact-original resolution remains idempotent. If the original identity cannot be established, escalate and keep replacement blocked. Existing uncommitted identities whose keys were never escrowed cannot be reconstructed from key hashes. An unreadable saved intent is retained for support reconciliation instead of overwritten.
7. Reconcile and retain the private case/evidence record under the approved retention policy. Never cancel/refund, change stock, mark a wallet paid or delete an order to repair recovery. No notifications are sent. Store the production signing key durably; current normal guest verification still accepts only one key. Rotation invalidates old guest capabilities and requires this authenticated/manual route where applicable; seamless multi-key rotation is not implemented or claimed. Keep mappings/consumed quotes needed for recovery, and never prune them merely because a quote expired.
